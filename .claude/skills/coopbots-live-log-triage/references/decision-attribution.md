# 从实机现象定位决策层

## 1. 建立同一场战斗的时间线

从归档中标出：种子/难度/层数/遭遇、席位与真人接管状态、入场血量/牌组/遗物/药水、每回合行动与选择、死亡/复活、敌人治疗/换形、结束状态。保留日志行号和实际 Card ID，中文名或 UI 描述不足以识别模型。

需要解释具体牌序时，记录动作前的手牌、费用、能量、抽弃消耗堆、状态层数、敌人意图、队友已行动情况及可选目标。日志没有这些信息就标为缺失，借助同场 replay/save 补充；终局卡组不能代替拿牌当时的卡组。

“只差一点血”先对账：初始血量 + 治疗/新增形态血量 - 有效伤害，与结尾剩余血量是否一致。过量伤害、敌方格挡、多人归因、换形和伤害统计遗漏都可能造成差额。外部退出/截断不等于团灭；可分析已发生的动作，但不能声称已知整场结局。

## 2. 按因果链分层，允许多个问题并存

| 层 | 足以推动下一步的证据 | 可判定的对照 | 常见代码入口（先 rg 确认当前版本） |
|---|---|---|---|
| 驱动与执行 | via=legacy、具名拒绝、搜到的路线未部署/被丢、UI 选择一直 pending | 同一可执行剧本是否真正发出、落地并继续；首次偏离在哪里 | KernelCombatPlanner、BotChoicePlanSync、CardChoicePatches、各房间 driver |
| 原生效果/模拟覆盖 | prediction-exception、boundary、力量/能量/升级/选择结果与游戏不同 | 单张卡/选择在原生规则与 KernelSession 分支的结果逐项比对 | KernelSession、Vendor/Prediction、效果镜像、KernelTurns |
| 候选、牌序与续演策略 | 卡合法且有收益，但首牌未入选、只在最后使用、根开局与续打偏好不同 | 同一根状态强制“先用/后用/不用”或 AB/BA；比较后续合法动作与终局 | KernelTournament.FirstActions、KernelRollout、KernelInvestmentProbe、KernelSequenceOrder、KernelExhaustPolicy |
| 搜索调度与结果保留 | 大量 continuation-budget、零完整路线、所有预算耗在前缀/嵌套预览、每瓶药后重搜 | 相同局面和总预算，比较完整终局数、候选覆盖、保存的参考与实际首牌 | KernelTournament、KernelJointTurnRun、KernelPotionContinuationRun |
| 局外效果估值 | 构筑认为收益高，实际效果未进入抽牌/支付/伤害模型；升级差值异常 | 拿牌/升级当时状态上的有无卡/升级前后对照，拆解分数来源 | BuildValue、CardProfile、DraftCardEffects、ConstructionHand、SustainedDeckValue、DeckStrength |
| 局外机会与选项 | 可选奖励/商店/营火/事件的替代方案更好，或牺牲生存换污染减少 | 同一菜单、金钱、血量和后续路线条件下比较合法替代；避免使用事后才知道的信息 | BotShopPlanner、RestSite 选择器、AncientOptionValue、事件 handlers、RoutePlanner |

先证明模型能兑现收益，再分析排序和预算。模型正确仍可能没被候选覆盖；终局比较正确仍可能丢掉胜利剧本；局内和局外可能同时有问题。不要强行把结论压成“局内/局外”二选一。

## 3. 本轮反复出现的机制怎样查

### 能力牌、力量/敏捷与先后顺序

- “拿到但不打”分开统计：在卡组、抽到手、当时可支付、进入候选、被选、真正打出。被倾泻/自动播放触发与主动出牌分开计数。
- 用相同根状态比较先投资与先输出，记录触发次数、未来能量/抽牌、队友收益、承伤与最终生存。回报期应落在实际还能存活的回合内。
- 主宰类层数兑现、熔岩之拳类翻倍、Panache 类按出牌触发，都比较 AB/BA 及必要的第三张兑现牌。不要为卡名固定“永远先/最后打”；先手斩杀和保命是反例。
- 当构筑高估但局内不使用，分别测试两侧。不能把构筑高分直接变成局内强制出牌奖励，也不能把没被打出直接当作烂卡证据。

### 消耗、弃牌与一次性资源

- 无攻击回合使用尖啸是调查线索；还要检查全部队友、消耗触发抽牌/格挡、永久成长等原生收益。
- 对照现在使用与保留到后续回合的机会成本。低威胁、致死威胁、触发收益分别建场景；不把保留偏好变成执行合法性拒绝。
- 弃牌/消耗可能让计划中的后续牌离手。比较必须以真实剩余手牌续打，不能继续计算已丢弃卡的收益。

### 战斗选牌遗物与药水

- 从原生调用确认选择来源、时机、min/max、能否不选，区分战斗中换牌/消耗/生成与永久删牌/拿牌。MinSelect=0 只表示允许空选，不是最优答案。
- 赌博筹码对照不换、部分换、全换的可支付手牌；预测与实机入口都要走到选择结果，且不接管真人。
- 替换抽牌只使用决策者可知的牌池；不要靠隐藏牌堆顶序作弊。旧日志缺失选牌结果时，缺日志不等于未选择，先补入口仪器。
- 药水比较包含瓶子消耗、满栏放弃奖励的机会成本及前后路线复用。按实际状态变化确认重搜是否必要，不能只数“用药次数多”。

### 抽牌、能量、减费和生成牌的升级

- 从原生升级差量开始：立即/下回合抽牌、立即/下回合能量、费用、生成牌数量、生命代价。字段存在不代表已进入最终模型。
- 跟踪完整计算链：效果资料 → 抽到的实际卡 → 是否付得起 → 实际打出 → 本人/队友收益 → 长战斗与污染修正 → 最终分数。
- 分别用资源紧缺和饱和手牌比较；多抽状态牌、无人可用的能量不必高分。队友输出不能套用本人的力量/触发次数，也不能制造本人的虚假斩杀来消除承伤。
- 输出升级前后分解，说明是哪一项抵消了收益。除非机制反例证明模型错误，不把所有能量/抽牌升级统一加常数。

## 4. 搜索效率的判读单位

以一场中的“席位、回合、决策点/根状态”为单位汇总，列出：搜索次数、实际墙钟、有效 compute、前缀数、rollouts、verified/终局类型、budget cutoffs、boundary、参考路线、实际选中的首牌。

- 完整模拟的失败也是有效比较结果；不要把 verified 全部叫胜利。比较真实胜利、真实失败与预算截断，防止一个中途看似血量高的截断覆盖已知胜利。
- nodes/前缀很多但完整终局为零，优先查预算分配、重复回放和嵌套预览。不能直接认定目标函数不重视长期收益，也不要只加总预算。
- stop=frontier-empty 表示当前保留的前沿耗尽；它不证明所有牌序已穷举或此战无解。需检查 TopK/剪枝/边界/候选；单纯延长同一次已结束搜索通常无效。
- 搜索行可能嵌套，父子 compute 不能重复相加；日志墙钟包括帧间等待，线程累计 CPU 与墙钟也不同。先检查当前 DLL 的字段写入点，确认不是构造时的零值或错误分母，再计算 GC 占比。
- 药水之后根状态确实改变时更新必要；可以复用的无药参考、候选前缀和已完成终局应单独核查。不要把“禁用所有重搜”当优化。

## 5. 反事实与结论强度

优先用同场原生 replay/save 重建动作前状态。当前仓库的知识恶魔例子可参考 `work/live-triage-20261003-evening/`、`tests/PatchSmoke/Fixtures/knowledge-demon-20261003.json`、`DecisionFixScenarios`、`CombatQualityScenarios`；这些是历史材料，不是下一场数据或固定阈值。

重建后先复现已发生的伤害/承伤和结尾，再每次改变一个因素。记录模型版本、根状态、牌序/选择、随机条件与同等预算；能跑出更优路线时用原生状态逐步重放，检查手牌、能量、目标、选择与死亡。由战斗开场卡组人工摆手牌的场景只能证明局部机制，不得称为完整历史重放。

三档表述：

- **已证实**：日志与原生对照指出具体差错，例如收益漏算、胜利路线被覆盖、合法选择入口没有执行。
- **较强嫌疑**：现象/预算统计支持某层，但缺少必要快照或可执行对照；写清下一步如何验证。
- **未证实**：只有总伤害低、没剩多少血、某张牌少用等相关性。扩大搜索没找到胜利也不证明无解。

报告按“现象与原文 → 决策层 → 可执行替代/缺失证据 → 预计影响及验证方法”列出问题；区分主因、放大因素与合理取舍。知识恶魔全选扣血可能减少污染但增加生存压力，不因团灭事后认定选项必错。

修复按机制家族扩展，并运行匹配的原生夹具、R2 和完整门禁。性能/数值快照因语义改变而需更新时保留前后差异；验收政策改变必须单独说明，不能把改断言冒充修好。受控测试提升与新实机胜率分开报告。
