# 战斗搜索延迟：移除长时/脚本化模式

## 背景

用户反馈两类现象：机器人在没有能量后仍出现长时间"深度思考"；深度思考结束后，每张牌之间仍有一次相同等待。前者与自动预算升级相关；后者可能来自排队脚本重放，也可能来自引擎动画与动作队列同步等待——日志为限频采样，无法在两者间给出确定归因。

## 原行为与问题

- **自动升级**：普通相位为 Depth9/Width8/节点768/200ms CPU/300ms wall（2 回合）；每轮人类结束回合后第一次搜索升级为 24/12/12288/4500ms/5000ms wall（3 回合）；全部人类死亡后进一步升级为 40/16/131072/28000ms/30000ms wall（16 回合）。最难路径单次搜索的调度上限达到 30 秒，且不因"已经无事可做"而缩短。
- **排队脚本重放**：搜索完成后把尾部动作存入队列，逐张无搜索执行。该保证并不成立：
  - 尾部在运行时选定真正第一个动作之前就已记录，首个动作可能被药水/旧规划器改写，尾部随之失真；
  - 尾部包含未来回合、内核不支持的药水步骤；
  - 复用时只校验下一张牌是否合法，没有校验世界状态是否与预测一致。
  - 因此不存在"整场最优脚本"的可靠依据。
- **Idle 判定命名误导**：`NoPlayableCard` 名字暗示只看手牌，实际把任意可用药水也算作"需要搜索"。旧代码的 `CanPlay` 本就允许 0 费/X 费牌，因此"无牌可打但有可用药水"仍会继续搜索；命名与注释没有反映这一语义，而保留免费牌可打的判定并非本次新增修复。

## 决策

- **移除**：自动长时/深度/单人生存预算升级；投机性排队计划重放（`deepRound`、`MaxDeepWallMs`、`MaxSoloWallMs`、pending 队列、`RememberSequence`/`HasPendingPlan`/`TryTakeNext` 及运行时 plan-step 分支）；误导性的 `SoloThinking`/`SoloExecuting` UI 状态。
- **保留**：普通有界多牌、跨机器人共享搜索；当前选牌同步；人类安全；药水规划（救援/legacy 路径不动）；每个动作后按真实棋盘重新校验与重新规划。
- **统一预算**：所有相位使用同一搜索形状 Depth9/Width8/节点768/200ms CPU/300ms wall（2 回合），按难度缩放节点与时间预算（Pro ×1.5，调度 wall 上限 450ms；Flash ×0.5）。人类结束回合或全部死亡不再提高预算。`IncludeEndTurns` 仍为 humansFinished，因此结束回合决策照常评估，但不再执行投机尾部。
- **廉价预检**：在 `KernelSession.Capture` 之前先检查是否存在**可实时打出的牌**或**可用战斗药水**。只要还有其一，搜索就继续——这正是旧 `CanPlay` 行为下 0 费/X 费牌与能量/抽牌/进攻药水仍会触发搜索的原因；仅当无牌且无可用药水时才立即返回 `Fallback`，不捕获、不搜索，设置 `LastNoAction = Idle` 并清除过期确认。能量为 0 不视为 idle（0 费/X 费可打）以及药水保留搜索，均为既有行为的保留而非本次新增修复。运行时的 idle 跳过逻辑继续保留。
- **诊断**：完成搜索输出一行 `search-complete: action=..., wall=..., compute=..., mode=..., actions=..., nodes=..., stop=...`，用于区分真实动画/队列等待与搜索耗时；由 `Report` 限频（每 5 秒最多一条），不会逐帧刷屏。其中 `compute=` 是处理过程内累计的 `Stopwatch` 耗时，并非真实 CPU 占用。

## 权衡与边界

- 本改动移除的是"保证数秒级模式"，不是规划引擎；有界搜索仍是启发式，**不宣称全局最优**，也没有全质量基准结论。现有测试验证的是战术正确性，不代表整局游戏性能。
- **移除成功的尾部复用会增加每个动作后的重新搜索**，因此整场战斗的累计单动作计算量可能上升；本改动改善的是响应性与过期脚本安全性，并非已被证实的整回合提速或质量提升。
- `wallBudgetMs` 是**调度上限**：`KernelSession.Capture` 与内核单步模拟动作不可抢占，**可能超出该上限**。引擎动画与动作队列同步等待仍然存在；测试无法据此断言游戏整体变速或质量提升。0.36.1 日志是限频采样：仅 47 条 wall 样本，其中 11 条超过 1s，最大 6875ms（log 第 14581 行，人类死亡后的单人分支）。这是限频且不完整的样本，不能据此得出完整延迟分布或质量结论。
- 有界模式对"药水-only 停顿"是安全的：药水存在时仍会搜索，只是搜索本身被限制在数百毫秒。
